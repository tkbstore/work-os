# 校正

`work-os-registry/release_lanes.toml` の閾値は「実測して決めた」という主張の上に立っています。
その主張を後から誰でも疑えるように、**測った対象と測った結果**をここに置いています。

```bash
python3 engine/calibrate.py --dry-run    # 宣言の矛盾だけを検査（clone しない）
python3 engine/calibrate.py --write      # 実際に clone して測り、results/ に書く
```

- 対象の宣言: [corpus.toml](./corpus.toml)
- 結果: [results/](./results/)（日付ごとの JSON）

観測は `engine/release_gate.evaluate()` をそのまま呼びます。校正のために観測を
書き直すと、校正した物差しと本番の物差しが別物になり、校正の意味が消えるためです。

コマンドは実行しません（他所のリポジトリのコードを走らせることになるため）。
そのため `test_passes` / `tutorial_runs` / `help_available` /
`test_command_declared` と、自組織のリポにだけ当たる `provenance` / `portability` は
**外部コーパスでは測れません**。後者は手元の 79 リポジトリで別に測っています（下記）。

## 2026-08-26 の結果

### まず、ゲート全体としては成立していない

チェック単位の差より先に見るべき数字があります。**1レーンでも欠けたら公開不可**という
設計なので、個々の差が小さくても全体では落ちます。群ごとの通過率はこうでした。

| 群 | 公開可 |
|---|---|
| 採られた（adopted 10本） | **3/10 (30%)** |
| 採られていない（not_adopted 6本） | **4/6 (67%)** |
| エージェント対応 CLI（6本） | **1/6 (17%)** |
| カナリア（hermes-agent 236k★ / claude-code 143k★） | **1/2 (50%)** |

**採られたリポより、採られていないリポのほうが通過率が高い。** ゲートとして逆向きに
効いています。カナリアは claude-code が落ちました。

落ちた理由の内訳:

- `anthropics/claude-code` — `install_section` / `runnable_example` /
  `contributing` / `command_appears_early` / `tests_exist` と robustness 2件。
  README が製品の入口として書かれており、手順は外にある形。
- `django/django` — README にコードブロックが無く docs へ誘導する形。
  最も採られた Python Web フレームワークが、入口レーンで落ちる。
- `NousResearch/hermes-agent` — **公開可**。落ちたのは `no_secrets_in_docs` と
  robustness の3件で、レーンとしては欠けていない。かつて `safety.no_secrets` が
  `agent/redact.py` の `private_key` / `db_url_creds` を漏洩として数えていた
  （秘匿処理のライブラリが秘匿パターンを持っていることを漏洩と読む誤検出）が、
  下の「誤検出を1つ直した」で秘密の判定を値の側へ置き直した結果、消えている。

`landmark` 群はカナリアであって統計ではありません（2本しかないので通過率は
比較に使えない）。**ここが落ちたら、疑うのはリポジトリではなく検査のほう**という
背理のために置いています。今は claude-code が落ちており、背理はそこで効いています。

### 誤検出を1つ直した。それでも結論は変わらなかった

`_match_glob()` が `**/` を展開できておらず、`**/tests/*` がトップレベルの
`tests/` にしか当たっていませんでした。`presets.fixtures`（テスト用の見本を除外する
宣言）が入れ子のレイアウトに対してほぼ無効だったということです。
ruff は `crates/ruff_linter/resources/test/fixtures/` の**意図的に壊したコード**を
101件拾われていました。修正後は 17件（残りは `resources/inline/err/` という
preset が知らない置き場）。

ただし、**この修正のあとも 24本中 9本しか公開可になりません**。つまり、ゲートが
逆向きに効いている原因はバグではなく検査そのものです。バグを直したことで、
その結論が強くなりました。

### この結果の限界

- **群が小さい**。各群 6〜10本なので、1本で 0.10〜0.17 動きます。
  `min_gap = 0.40` は「2〜3本ぶんの差」という程度の粗さです。
- **対照群は組織所有だけ**です（個人の趣味リポを悪い例として名指ししないため）。
  組織が作ったものは star が少なくても整備されている傾向があり、
  それが「整備の痕跡が分けない」という結果を押し上げている可能性があります。
- **執行に使う値は測れていません**。`command_exit_zero` 系は校正の対象外です。
  「テストが通ること」「チュートリアルが動くこと」が採用と相関するかは、
  この方法では答えられません。

### この日の枠組みは誤っていた

上の表は「採られたか（star が多いか）」でチェックを採点しています。しかしゲートが
答えるべきなのは**許可の問い**——「これを出していいか」——であって、人気の予測では
ありません。この取り違えのために、「群を分けないチェックには根拠がない」と読んで
しまいました。

分けないことが直ちに根拠の欠如を意味するのは、その閾値が**分離の観測から来た場合
だけ**です。`license_exists` が両群とも通るのは全員が持っているからで、無ければ
法的に誰も使えない以上、その検査は正しい。分離を根拠にしてよいのは star 研究に
由来する3つ（`command_appears_early` / `usage_section` / `install_section`）に限られます。

正しい測り方は**偽陽性と偽陰性**です。出せるものを落としたか、出せないものを通したか。
ラベルは外から探さなくても手に入ります。すでに公開され他人の手に渡っているリポジトリは
「出してよい」の正解であり、手元のリポジトリは実物を1件ずつ開けば正解が確かめられます。

## 2026-08-26（続き）: 手元の 79 リポジトリで偽陽性・偽陰性を数えた

外部コーパスは「出してよい」側の例しか持ちません。**落としてはいけないものを落として
いないか**は測れても、**通してはいけないものを通していないか**は測れない。そこで
手元の全リポジトリ（79本）にゲートを当て、当たった1件ずつを実物で確かめました。

### 分かったこと 1: 判定に一番効くレーンが、判定対象で走っていなかった

`provenance` の2つの観測が `only_when_declared = true` だったため、**79本中77本で
skip** されていました。`[publish]` を書いた自リポにしか当たらない条件です。
境界の置き方が間違っていました。問うべきは「宣言があるか」ではなく
**「自組織のリポか」**です。`only_when_owned` に置き直しました。

### 分かったこと 2: 秘密の検査は 7 件中 6 件が誤検出だった

| 当たったもの | 実物 | 判定 |
|---|---|---|
| PEM 秘密鍵ファイル | `-----BEGIN PRIVATE KEY-----` 52 行 | **真** |
| `api_key` | コメントアウトされた `"YOUR_..._API_KEY"` | 偽 |
| `db_url_creds` ×3 リポ | `user:user@db` / `@localhost` / `local-only-password@db` | 偽 |
| `aws_access_key` | vendor された botocore のサンプル JSON | 偽 |
| `google_oauth` ×4 リポ | 手順書の穴埋め見本 `GOCSPX-xxxxx` | 偽 |

原因は共通で、**変数名や接頭辞で秘密を判定していた**ことです。秘密かどうかを決めるのは
値のほうです。3つの原理に置き換えました。

1. **到達性** — 資格情報が危ないのは、それが外から届くホストに対して通用するときだけ。
   ホスト名にドットが無ければ、その名前はそのネットワークの中でしか解決しない。
2. **見本かどうか** — `YOUR_...` `<...>` `CHANGE_ME` `ALL_CAPS_WITH_UNDERSCORES` は
   埋めてもらうために置かれたもので、置いてあること自体が作法である。
3. **著者性** — vendor した木・ビルド成果物・lock ファイルは自分のコードではない。
   `presets.vendored` として一度に引く。拡張子ごとに逃がすと逃がし忘れる。

結果: 誤検出 6 → 0、真陽性 1/1 を維持。

### 分かったこと 3: 絶対パスの検査は 7 割見逃していた

`globs` が `.py .ts .js .sh .toml` の列挙だったため、`.md` `.json` `.yaml` に書かれた
ホームディレクトリを展開した絶対パスを素通りさせていました。実際に含んでいた 23 本のうち **16 本を pass**。
拡張子を3つ足すのは同じ間違いを繰り返すだけなので、`**/*`（自分が書いたテキスト全部）に
当てて、他人が書いた木だけを引く形にしました。

この観測は `provenance` から `portability` レーンに移しました。「自分のものとして
出せるか」と「他人のマシンで動くか」は別の問いだからです。

**ここで一度、検証の仕方を間違えました。** 「ゲートに依らない独立の grep と突き合わせて
偽陽性 0」と書きましたが、その grep は**ゲートと同じ正規表現**を使っていました。
照合できたのは「同じ物差しを2回当てて同じ答えが出る」ことだけで、物差し自体の誤りは
原理的に見つかりません。当たった 275 件を実物で1件ずつ見て、はじめて分かりました。

  本物のホームパス          248 件
  http URL の中（誤検出）    27 件  ← 2 リポジトリはこれだけで落ちていた

`/home/` で始まる並びは、web の URL の中に現れれば web のパスであって誰かのホームでは
ありません（`file://` は本物です）。パターン側を複雑にすると読めなくなるので、
engine に `except_within`——**この文脈の中の一致は数えない**——を足し、文脈のほうを
config で宣言する形にしました。

教訓として残しておきます。**独立の検証と呼べるのは、独立した観測を使ったときだけです。**
同じ規則を2回走らせるのは再現であって検証ではありません。

### 分かったこと 4: 語のリストが2つの仕事を兼ねていた

`private_terms.toml` は work-os の公開層を抽象に保つためのリストです。それをフリート
全体に当てると、自社製品名（あるリポでは 1877 回）や LICENSE の著作権者名まで漏洩に
数えます。ゲートが見るべきは `[clients]` だけ——**外販物に同梱するとき、他の顧客の
名前が入っていたら渡せない**——で、残りは `engine/abstraction_gate.py` の管轄です。

### この測り方の限界

- **偽陰性のラベルは「見つけた分」しかない**。独立の grep で照合できたのは絶対パスと
  既知の秘密の形だけです。誰も思いついていない形の漏れは、ここでも数えられません。
- **顧客名は相手によって可否が変わる**。ある顧客のためのリポにその顧客の名前が
  在るのは当然です。いまは所有の宣言でしか区別できないので、リポが自分の担当顧客を
  宣言する仕組みが要ります。未着手。
- **実行レーンは相変わらず測れていません**。他所のコードを走らせないという制約は
  そのままです。
